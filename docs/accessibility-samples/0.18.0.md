# Screen-reader sample for 0.18.0

This is the pre-release sample for AutoDJ 0.18.0. The full run was taken on commit 2e42078;
the later checks below cover the fixes up to the release commit. It covers the twelve flows listed under "Release sampling" in
[Accessibility testing](../accessibility-testing.md) with NVDA and Chrome, and a subset of them with
NVDA and Firefox and with NVDA and Edge. The results apply only to the pairings, flows and steps
described below. It replaces an earlier draft sample of 0.18.0 (commit f10050e); none of that
draft's results are reused here.

## What 0.18.0 ships with

This summary reflects the last check on 2026-09-28 (master cfb3ac7, see "Auto-play and D14
check (2026-09-28)" below), on top of the final verification (master c9f54ff). It covers only the
pairings and steps recorded here.

- Fixed and verified: D1, D2, D3, D5 to D13, D15, D16, D17 and D18. D16 and the D18 Listen here
  and mute steps were checked by NVDA speech in the final run. D15, D17 and D18 were also checked
  by reading the page's audio state, because they concern volume and playback.
- Accepted as designed: D4. The pairing dialog's name and instructions are spoken twice when it
  opens, as they are for any named dialog in these browsers.
- Accepted as a known NVDA and Chrome quirk (owner decision, 2026-09-28): D14 (minor, improved
  twice). After Delete profile, Revoke or Clear queue is
  confirmed in the page's own dialog, NVDA no longer reads the page title, "unknown" or the button
  that opened the dialog. It still reads one stray line from the top of the page (for example
  "banner landmark heading level 1 AutoDJ" or "same page link Skip to main content") before the
  new focus target. The same line is read when the dialog is closed with Cancel or Escape, so it
  comes with closing the dialog, not with the delete.
- Media Play key on a page where Play was not pressed: fixed in 25a81dc and checked in Chrome and
  Firefox by page state (pass). This is the likely cause of the unexplained Firefox playback in the
  final verification. A real operating-system media key was not sent.
- Not covered: Narrator, forced colours, and NVDA+key commands. No person listened; an automated
  agent captured NVDA's speech.

## Setup

- Date: 2026-09-27 22:51 to 2026-09-28 00:04 local time (MDT).
- Operating system: Windows 11 Home 25H2, build 26200.9457.
- Screen reader: NVDA 2026.2 (AMD64), laptop keyboard layout. The synthesizer was
  ETI-Eloquence at the start. Someone at the machine switched it to "No speech" at 22:56 and to
  eSpeak NG at 23:09 (see Method). The capture records what NVDA sent to speech, so the change
  of voice does not change the quotes below.
- Browsers:
  - Google Chrome 153.0.8010.53, in the separate automation profile run by the chrome-devtools
    MCP server.
  - Mozilla Firefox 156.0.1, in a separate automation profile started by the firefox-devtools MCP
    server.
  - Microsoft Edge 154.0.4258.37, started by the agent with a new, empty profile in a temporary
    folder. Edge signed that profile in to the machine's Microsoft account on its own and showed
    a sync notice; the profile was deleted afterwards.
- Narrator: not sampled. The screen-reader-testing MCP server listed only NVDA
  (`list_readers` returned one reader, "nvda"), so there was no way to connect to Narrator or
  capture its speech.
- AutoDJ: version 0.18.0, build 2e42078, with the web bundle built from that commit
  (`npm run build`; build-info 0.18.0). The server ran from a temporary folder with its own
  `config.toml`: music folder `Z:/Beetsmusic` (the NAS share, read only), index folder a local
  copy of the owner's 76,728-track index, port 8093. It ran as `autodj serve --lan` (pairing on,
  browser audio) for most flows, and as `autodj serve --lan --stream` (pairing on, stream mode,
  no server audio) for the stream flow and the Sonos check. The browsers used
  `http://localhost:8093`.
- Volume: the owner uses a screen reader at this machine, so the page volume was set to 5 percent
  or lower before anything played, and playback was paused whenever a step did not need it. The
  server had no sound output in either mode. The stream was read by a script, not played aloud.

## Method

No person listened to this sample. An automated agent (Claude, run from Claude Code) drove the
browsers and recorded what NVDA spoke:

- Speech was captured through the screen-reader-testing MCP server in "live" mode: NVDA kept
  speaking and the server's NVDA bridge logged each utterance with a timestamp. The quotes below
  come from those logs. Where the record says NVDA spoke something twice, NVDA's own log
  (`speech.speech.speak`) was checked and shows two separate speak calls.
- The bridge ends a session after two minutes, so the agent reconnected before most steps. Each
  reconnect left a gap of about half a second in the capture. No quoted step fell in a gap.
- Keys:
  - Chrome: keys went to the page through the Chrome DevTools Protocol. The page received real key
    events, but NVDA's own key handling was bypassed. Steps marked "real keys" were sent as
    Windows key presses (SendInput through the windows-mcp server), which NVDA handled as
    keyboard input.
  - Firefox: keys went through the firefox-devtools server (WebDriver). Firefox's open drop-down
    list is outside the page and did not receive those keys, so that step used real keys.
  - Edge: every key was a real Windows key press.
  - The Insert key did not reach NVDA as a modifier through windows-mcp (NVDA logged
    `insert+tab` as plain Tab), so NVDA+F2 pass-through and other NVDA+key commands could not be
    exercised. In Edge the single-key hotkeys were sent while focus was on the volume slider,
    where NVDA is in focus mode and passes letters to the page.
- The agent used page scripts for setup and to read state, never to decide what NVDA said:
  setting the volume slider to 5 percent before playback, reading which element had focus,
  moving focus directly to a control in about a dozen places to save long Tab sequences (named in
  the steps below), and filling the History with 53 entries by calling `/api/skip` 50 times with
  the page silent.
- Owner activity: someone at the machine used it three times during the run. At 22:56 they
  switched NVDA's synthesizer to "No speech" (NVDA+Control+S). At 23:09:43 they switched it to
  eSpeak NG while the agent was tabbing into Settings, so speech between 23:09:43 and 23:09:46 is
  excluded. From 23:10:55 to 23:14:07 they used other windows (closed TeamTalk, typed in another
  window). The agent paused, resumed after 60 seconds without input, and repeated the affected
  steps. No result below depends on input the agent did not send.

## Verification of fixes (2026-09-28)

A second, targeted run checked the fixes for D1 to D14 on master e2c6cd9 (the 0.18.0 code plus

  server rounds the volume gain to two decimals (`src/autodj/_bridge.py` line 817), and the page

  Any setting below about 23 percent comes back as 0: Shift+V said "Volume 0 percent" at 5
  percent, focus on the slider said "0", the focused slider said "0" by itself about a second

## Limits

- No person listened. The method section explains how keys were sent and how speech was
  captured. Most Chrome and Firefox steps bypassed NVDA's own key handling.
- NVDA+F2 pass-through and other NVDA+key commands could not be sent, so browse-mode use of the
  hotkeys was not sampled.
- Narrator was not sampled; the MCP server offers only NVDA.
- Forced colours were not sampled; speech capture cannot test them.
- Firefox and Edge were sampled for the subset of flows named above only. Stream mode, voice
  liners, EQ, History, Why this track, lyrics and the track-change opt-in were sampled in Chrome
  only.
- No library job could be left running for several minutes. Analyse finished in 35 seconds
  because the index was already analysed, Enrich fails without a beets database, and Index would
  have downloaded the embedding model. The longest run was Prune, 58 seconds, with start and end
  spoken once each.
- Session expiry was tested by signing out, not by a session timing out. "Make new link" was not
  pressed.
- Volume was kept at 5 percent or lower and was set by script before each playback, so the volume
  slider was only sampled between 0 and 8 percent.
- The History had 53 entries, filled by skipping tracks through the API with the page silent.
- The owner used the machine three times during the run (see Method); the affected steps were
  repeated.
- The second verification captured no NVDA speech (an NVDA dialog held the foreground), so its
  D14 and D16 results are unverified and its D17 and Liner Test results rest on live-region text
  and engine state. The Edge revoke step of D14 was not run.
- The final verification checked D14, D16 and D18 with NVDA in Chrome (and D16 in Firefox) only.
  The Edge revoke step of D14 was again not run, because the Edge window could not be brought to
  the foreground; the revoke was checked in Chrome. D18 was checked in Chrome only. The Firefox
  playback start described there was not reproduced.
- The auto-play and D14 check sent Media Session actions by calling the page's own handler from
  DevTools, not with a real media key, so how Windows routes the key between browsers was not
  tested. Its D14 steps were in Chrome only.
