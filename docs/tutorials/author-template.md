# Tutorial author template

This is an author scaffold, not a lesson to follow. Copy its section structure
into a new file in this directory, replace the drafting instructions with
reader-facing prose, and remove unused sections. Do not publish empty sections
or author notes in a lesson.

Follow [Writing documentation](../../CONTRIBUTING.md#writing-documentation).
For the next planned lesson, use the outcome and prerequisites in the
[tutorial roadmap](README.md). Extend the same Practice station rather than
starting an unrelated example.

## State what the reader will learn

Replace the page title with the reader's goal. Open with the one capability the
reader gains and the observable result that demonstrates it. State the starting
state separately. Name the capability assumed from any earlier lesson and link
to that lesson only if its file exists.

## Before you begin

List necessary tools, music, access, and prior knowledge. Link to installation
or setup instructions rather than copying them. Name the playback mode and any
network or provider requirements. Say whether the station must have no listeners.

Explain what the reader will create or change before the first action. Include
saved settings, files, background work, and any network or paid-service activity.
Explain how to stop safely before starting a long-running activity.

## Walk through one worked example

Replace this heading with the first concrete learning step. Repeat the following
pattern for each meaningful stage, using descriptive headings rather than a
fixed inventory of labels:

1. Explain what this stage adds to Practice. Define unfamiliar terms when needed.
2. Give the smallest complete set of steps, using exact labels and explicit saves.
3. State the expected text or observable state, including normal variation.
4. Explain what that result establishes and what it does not establish.
5. Give a likely failure, how to confirm its cause, and a worked recovery.

Use keyboard-operable controls and nonvisual observations. Listening can be part
of a playback lesson; also identify the title, state, history, or other text that
lets readers inspect what happened. Link to longer explanations after a completed
stage. Keep essential instructions and recovery in the main reading flow.

## Try a small change

After the worked example succeeds, ask the reader to change one thing, predict
the result, try it, and explain the observation. Give expected behavior and the
reason after the prompt so the reader can check their understanding. Do not
withhold help on first contact or turn recovery into a guessing exercise.

## Stop and keep or remove your work

Give exact steps to stop playback or other activity. Explain which resources
remain, which later lessons reuse them, and what any optional removal does.
Include a check that the activity stopped. Avoid destructive cleanup unless it
serves the lesson, and explain its consequence before the action.

## What you can do next

Name the gained capability and link to relevant task guides, reference, or
explanation. Link the next lesson if available; otherwise describe it as planned
and link to the roadmap. Include the repository's AI disclosure when applicable.

## Review before offering the lesson

This section is for authors; keep review evidence in the PR or issue, not in the
finished lesson. Check labels, prerequisites, results, recovery, and cleanup
against the actual application. Check page links and heading fragments,
including new untracked files excluded by the native checker.

Walk through the rendered lesson and application with a keyboard and screen
reader. Record the revision, environment, date, findings, and what was actually
tested. Fix findings and repeat affected steps. Report missing manual review as
pending; source inspection and automated checks do not establish that review.
